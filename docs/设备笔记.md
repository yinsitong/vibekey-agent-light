# AU05 设备笔记

> 实测环境：macOS 27.2.1 / Ulanzi Studio 3.4.8 / 设备固件 TX·RX 4.6.3。

## 一、结论摘要

| 通道 | 能不能用来做状态指示 |
| --- | --- |
| Ulanzi Studio 官方「工作模式 + Agent 状态同步」 | ❌ 收到事件但不做映射，灯不变 |
| 工作模式的**单颗灯**（type 常亮/呼吸 + 逐灯亮度） | ❌ 写入读回都正常，物理灯不动 |
| 全亮模式的**整机亮度** | ✅ 有效，旋钮 + 三颗按键一起亮 |
| 反复写两个不同亮度值 | ✅ 能做出可见的闪烁/呼吸 |
| RGB 变色 | ❌ `getDeviceSupportLedEffect`(01 06 39) 返回全 0 |

设备只有暖白单色。

## 二、官方通道为什么不工作

Studio 会给本机的 Claude Code / Codex 自动装 hooks
（`~/.claude/settings.json`、`~/.codex/hooks.json`），hook 脚本最终只是执行：

```bash
ustudio-cli --agent <id> --event <事件名>    # stdin 喂 JSON
```

实测这条 CLI 完全可用（rc=0，Studio 收到）。但抓
`~/Library/Application Support/UlanziStudio/logs/*_sdk.log` 发现，Studio 每收到一个事件只做：

```text
setDeviceIndicatorLightWorkModeType  ×3    → 读回 ledIndex 1/2/3 = workType 0/0/1（原值）
```

即**回写原值，从不按状态下发**；也从不碰 index 0（唯一配了呼吸的那颗）。
所以灯不会变。这是 Studio 设备侧实现的问题，不是 Agent 侧。

Proma 自身没有 hook 体系（`Proma.app/Contents/Resources/app.asar` 里 `PreToolUse` /
`hookEventName` 命中数为 0），但监听层是 CLI，谁都能冒充上报——所以 Proma 用不用得上
跟有没有 hook 无关，瓶颈在 Studio。

Bridge 仍然每次顺带发一份 Studio 事件，等 Ulanzi 修好后能自动接上。

## 三、灯效寄存器

读全部参数：`01 0b 88 01`（24 字节有效）

```text
byte 0-1  保留
byte 2    currentMode    0=全灭 1=全亮 2=工作
byte 3    allOnBright    0..20（写 21 会被当成灭）
byte 4+   workModeDatas  每颗灯 5 字节 × 4
          [btn1, btn2, btn3, dial]
          每块 = type, workTime, breatheLevel, breatheBright, alwaysOnBright
          type: 0=灭 1=常亮 2=呼吸
```

写工作模式单颗灯必须带 **focus 索引**，一次只改一颗：

```text
01 0b 88 04 | 7c <focus> 00 00 | 四块完整数据
```

`ledrestore` 走 focus=0，所以改旋钮（index 3）不会生效。

## 四、踩过的坑（按踩的顺序）

1. **以为灯不受软件控制**——实际是写了越界的亮度 21。写 21 不报错、读回 21、物理灭。
   判断标准：任何亮度值先按 0–20 夹紧。
2. **单颗灯控制无效**：type=1/2、亮度 2/7/21 全试过，肉眼不动；0.5 秒交替闪 15 次也看不到。
   只有全亮模式的整机亮度真正驱动可见亮度。
3. **呼吸 `type=2` 在本固件上表现为熄灭**。
4. **同值不重施加**：写 `mode 1 20` 第一次有效，之后再写就物理无效，即使中间切过一次模式。
   寄存器读回一切正常——最容易误判成"控制成功"。
   做闪烁必须交替写两个不同值。
5. **待机会骗人**：`StandbyTime=300s`，5 分钟无操作进待机，此时厂商口读写照常返回成功但灯不动。
   早期两次「灯灭了」被误判成控制生效，其实是待机。
6. **旋钮那圈常亮微光**像硬件连接指示灯（文档 1.3.1「连接成功后设备旋钮灯常亮」），
   软件改不动；能控的 index 3 可能是另一个几乎不可见的点位 LED。

## 五、HID/协议来源

开源项目 **OpenVibeKey**（`palaemonboy/OpenVibeKey`）逆向出了 VibeKit，
本项目的 `vendor/` 就是它的 Swift 包（`Sources/VibeKitCore/Resources/protocol-commands.json`
是协议命令表，118 条）。

本项目的 `bin/vibekit-led` 是在 `Sources/VibeKitWrite/main.swift` 里加了自定义子命令后编译的：

| 子命令 | 作用 |
| --- | --- |
| `busy <level>` | 全亮 + 亮度（先写 level-1 再写 level，制造值变化） |
| `pulse <n> <ms> <lo> <hi>` | 闪 n 下 |
| `pulse-loop <ms> <lo> <hi> <burst> <gap>` | 持续闪，供桥当子进程用 |
| `mode <0\|1\|2> [bright]` | 切整机模式 / 设亮度 |
| `dial <0\|1>` | 旋钮那颗灯开关（视觉上无效，保留供排查） |
| `dialcfg <type> <ao> [bb]` | 直接写旋钮块的三个亮度字段 |
| `flash <n> <ms>` | 快速闪（工作模式下无效） |
| `dump88` | 打印 24 字节带下标 |

原始设备参数（出问题时用来恢复）：

```text
mode=2(工作)  allOnBright=20  types=[2,0,0,1]
旋钮块 = [1, 10, 2, 2, 2]
```
